## 阶段 0：项目启动

阶段结论：

```text
系统定位已明确，可以进入结构化设计阶段。
```

已确认事项：

```text
系统名称：个人知识问答系统。
系统用途：帮助用户将日常生活、工作和 AI 对话中的知识沉淀为可学习、可练习、可评估、可追溯的问答体系。
目标用户：MVP 阶段服务用户本人。
未来扩展：预留多用户能力，核心业务对象保留 user_id。
交付物类型：Web/API 服务 + 外部 Agent API/MCP 接入能力。
当前仓库：已由用户手动创建 Git 仓库。
当前已有文档：业务建模文档、问答头脑风暴记录。
```

待确认事项：

```text
系统最终技术栈。
MVP 是否先做 Web 页面 + API，还是先做 API + MCP 后台能力。
部署环境：本机、Docker、服务器或云服务。
```

风险点：

```text
如果过早进入实现，容易把 API、MCP、题库、评分、审计揉成一个大模块。
外部 Agent 接入依赖不同工具是否能稳定传递会话上下文。
```

下一步动作：

```text
确认业务建模文档后，进入领域模型和系统边界细化。
```

## 阶段 1：需求分析

阶段结论：

```text
核心需求已形成，MVP 范围已初步明确。
```

已确认事项：

```text
知识入口包括主题学习、即时掌握、外部会话沉淀。
知识沉淀由用户主动触发，不自动污染知识库。
题型 MVP 支持主观问答和选择题。
认知维度包括理解、区分、应用、分析、评价。
难度等级为 1-5。
掌握度采用分数、等级、诊断标签和五维画像组合。
AI 评分后用户可以确认或修正。
错误集记录错题、薄弱知识点和错误原因。
题目、答案、评分规则、核心讲解需要版本化。
外部 Agent 通过 API/MCP 接入，Agent 侧 MVP 只做轻量确认。
所有生成内容默认待确认，用户明确要求时可直接正式入库。
质量校验必须包含规则校验、AI 校验、自动修正、用户最终确认。
```

待确认事项：

```text
MVP 第一版是否必须包含外部 Agent MCP 实际可调用工具，还是先实现 API 并保留 MCP schema。
即时掌握模式的小测题默认数量是否固定为 2-3 道，还是按知识点复杂度动态变化。
正式练习是否先支持一题一答，批量练习是否作为后续功能。
```

风险点：

```text
需求能力较多，MVP 需要严格聚焦核心闭环。
题目质量高度依赖大模型，需要通过模板、校验和用户确认降低风险。
```

下一步动作：

```text
把需求分为 must / should / could，并形成 MVP 功能优先级。
```

## 阶段 2：领域建模

阶段结论：

```text
初版领域模型已建立，需要继续细化实体关系、状态机和不变量。
```

已确认事项：

```text
核心层级：User -> KnowledgeDomain -> KnowledgeTopic -> KnowledgePoint -> Question。
知识点包含 KnowledgeType，MVP 六类：概念类、操作类、原理类、场景应用类、方案评价类、事实信息类。
核心讲解分为知识点通用讲解和题目补充讲解。
Question、AnswerVersion、ScoringRubricVersion、CoreExplanationVersion 都需要版本化。
MasteryProfile 支持 domain / topic / knowledge_point 三个层级。
SourceReference 记录来源内容、来源系统、可信度。
GenerationRecord 记录 AI Agent、模型、提示词版本和生成参数。
QualityCheckRecord 记录校验模型、校验指标、结果和修正建议。
AuditEvent 记录生成、确认、编辑、答题、评分、修正、归档等事件。
```

待确认事项：

```text
是否需要单独的 IngestionTask / ReviewQueue 对象承载待确认沉淀流程。
QuestionVersion、AnswerVersion、ScoringRubricVersion 之间是一对一当前版本绑定，还是允许一个题目版本对应多个答案版本。
临时题答题记录确认入库后补计入掌握度时，是否需要生成单独的 recalculation event。
```

风险点：

```text
版本化对象较多，如果关系不清晰，后续实现容易出现历史评分追溯混乱。
掌握画像是派生数据，需要明确重新计算策略和数据来源。
```

下一步动作：

```text
绘制 ER 图和状态机，明确实体关系、主外键、派生数据和状态流转。
```

## 阶段 3：系统边界

阶段结论：

```text
系统边界方向已明确，但需要在 API/MCP 细化阶段落到契约。
```

已确认事项：

```text
知识问答系统后端 API 是核心业务底座。
MCP Server 是外部 AI Agent 接入层，不承载核心业务逻辑。
外部系统包括 Codex、Claude Code、ChatGPT、Claude、未来文档导入工具。
外部 Agent 提交会话沉淀后，系统返回主题建议、知识点列表、题目预览和确认/编辑链接。
```

待确认事项：

```text
外部 Agent 是否能够传入完整会话、最近 N 轮会话、选中片段或摘要。
外部 Agent 调用知识问答系统时如何认证。
确认链接是本地 Web URL、桌面应用深链，还是普通 HTTP 页面。
```

风险点：

```text
外部 Agent 可获取的上下文能力不一致，MCP Tool 需要支持多种 context 输入形态。
从外部会话进入系统时需要避免泄露敏感内容。
```

下一步动作：

```text
设计外部会话沉淀 API 和 MCP Tool schema。
```

## 阶段 4：架构设计

阶段结论：

```text
推荐采用模块化单体作为 MVP 架构，API 与 MCP 作为边界适配层。
```

已确认事项：

```text
架构建议：模块化单体。
核心模块建议：用户与设置、知识结构、生成与入库、题库与版本、练习与评分、掌握画像、质量校验、来源溯源、审计日志、外部接入。
通信方式：系统内部同步调用为主；外部通过 HTTP API；Agent 通过 MCP Tool 调用。
存储建议：MVP 优先关系型数据库，便于版本、审计、状态流和关联查询。
```

待确认事项：

```text
技术栈：后端语言和框架。
数据库：SQLite、PostgreSQL 或其他。
是否需要向量库用于后续文档导入和语义检索。
是否需要后台任务队列处理题目生成、质量校验和掌握画像重算。
```

风险点：

```text
如果一开始引入过多基础设施，会拖慢核心闭环验证。
如果完全同步处理 AI 生成和校验，用户等待时间可能较长。
```

下一步动作：

```text
在 ER/API 设计后，选择最小可用技术栈和模块边界。
```

## 阶段 5：数据设计

阶段结论：

```text
业务对象字段已初步整理，需要推进为 ER 图、表结构、索引和约束。
```

已确认事项：

```text
所有核心业务对象需要 created_at 和 updated_at。
所有核心业务对象字段在文档中使用英文名，并补充简体中文名。
核心对象预留 user_id。
版本化对象需要 version_no、status、created_at、updated_at。
审计和溯源对象需要记录 Agent、模型、提示词版本和来源。
```

待确认事项：

```text
是否统一使用软删除字段 deleted_at。
status 字段枚举是否统一建字典。
JSON 字段的使用范围，例如 options、generation_params、issues、metadata。
掌握画像是每次答题实时更新，还是异步重算。
```

风险点：

```text
字段过度 JSON 化会降低查询和审计能力。
字段过度拆表会增加 MVP 实现复杂度。
```

下一步动作：

```text
输出 ER 图和表结构草案。
```

## 阶段 6：接口设计

阶段结论：

```text
接口方向已明确，尚未形成 API 草案和 MCP Tool schema。
```

已确认事项：

```text
核心 API 需要覆盖知识结构、沉淀任务、题目生成、质量校验、确认入库、练习答题、评分反馈、掌握画像、错误集、来源审计。
MCP Tool 候选包括 qa_create_from_conversation、qa_create_instant_check、qa_search_topics、qa_attach_to_topic、qa_get_review_queue、qa_confirm_ingestion。
```

待确认事项：

```text
API 版本策略。
错误响应结构。
分页、过滤、排序规则。
幂等键策略，尤其是外部 Agent 重复提交。
MCP Tool 返回给 Agent 的题目预览长度限制。
```

风险点：

```text
如果 API 过早暴露内部表结构，会导致后续重构困难。
外部 Agent 重复调用可能造成重复沉淀任务。
```

下一步动作：

```text
输出 API 草案和 MCP Tool 输入输出 schema。
```

## 阶段 7：核心流程

阶段结论：

```text
关键流程已识别，需要补充异常路径、重试、补偿和审计点。
```

已确认事项：

```text
主题学习流程：主题 -> 大纲 -> 知识点 -> 讲解和题目 -> 校验 -> 待确认 -> 正式入库。
即时掌握流程：问题 -> 解释 -> 小测 -> 评分 -> 可选沉淀。
外部会话沉淀流程：Agent 提交 -> 提取知识 -> 生成候选 -> 返回预览和链接 -> 用户确认。
答题评分流程：用户答题 -> AI 评分 -> 用户确认或修正 -> 更新掌握画像。
质量校验流程：规则校验 -> AI 校验 -> 自动修正 2-3 次 -> 用户确认。
```

待确认事项：

```text
AI 生成失败时是否保留失败任务记录。
质量校验超过重试次数后，用户是否能手动编辑并重新触发校验。
来源冲突确认流程如何进入待确认队列。
```

风险点：

```text
长流程包含 AI 调用，可能出现部分成功、部分失败。
多次自动修正可能产生多个版本，需要明确哪个版本进入待确认。
```

下一步动作：

```text
为核心流程绘制状态机和序列流程。
```

## 阶段 8：安全设计

阶段结论：

```text
安全要求尚未细化，MVP 也需要至少覆盖认证、输入校验、敏感数据和审计。
```

已确认事项：

```text
外部 Agent 接入需要认证。
外部会话、文档、用户答案可能包含敏感内容。
敏感操作需要审计事件。
```

待确认事项：

```text
MVP 是否需要账号登录，还是本地单用户免登录。
API Key、Bearer Token 或本地信任方式如何选择。
是否需要对来源内容和用户答案做脱敏。
模型调用密钥如何配置和保护。
```

风险点：

```text
外部会话内容可能包含隐私、密钥或项目敏感信息。
日志如果直接记录完整提示词和答案，可能泄露敏感信息。
```

下一步动作：

```text
在 API/MCP 设计中加入认证、授权、输入校验和日志脱敏规则。
```

## 阶段 9：可观测性

阶段结论：

```text
系统天然需要业务审计，可观测性应从 MVP 开始保留关键事件。
```

已确认事项：

```text
审计事件需要记录生成、确认、编辑、答题、评分、用户修正、版本更新、质量校验、自动修正、归档、废弃和来源冲突处理。
GenerationRecord 和 QualityCheckRecord 可用于后续分析模型生成质量和校验质量。
```

待确认事项：

```text
是否需要应用运行日志、业务事件日志、审计日志分离。
是否需要为 AI 调用记录耗时、token、成本。
是否需要健康检查接口。
```

风险点：

```text
只记录结果不记录过程，会影响后续追溯模型质量。
记录过多原文可能带来隐私风险和存储成本。
```

下一步动作：

```text
设计日志、审计事件和 AI 调用指标字段。
```

## 阶段 10：开发计划

阶段结论：

```text
建议先实现最小核心闭环，再扩展外部 Agent 和复杂分析能力。
```

已确认事项：

```text
核心闭环应优先覆盖：创建领域/主题/知识点 -> 生成讲解和题目 -> 质量校验 -> 待确认 -> 正式入库 -> 答题 -> AI 评分 + 用户修正 -> 掌握画像更新。
外部 Agent 接入是重要目标，但可先 API 化，再 MCP 包装。
```

待确认事项：

```text
第一阶段是否实现真实 AI 调用，还是先用 mock 生成器验证流程。
第一阶段是否需要 Web UI，还是先用 API/CLI 验证业务闭环。
```

风险点：

```text
如果第一阶段同时做 Web UI、API、MCP、AI 生成、审计和画像，范围会过大。
```

下一步动作：

```text
用户确认后，拆分 MVP 里程碑和验收标准。
```
